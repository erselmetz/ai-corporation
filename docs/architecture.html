API boundary

The CLI also uses CorporationApplicationService. FastAPI provides Corporation status, Employee/Agent, Provider/Model assignment, Task, Project, and read-only Activity resources. Resource routes call the service, which delegates to the existing Core; routes do not access registries or logging storage directly. The default authentication backend rejects requests until an application supplies one. Protected resources check their declared permissions; this is an injectable security foundation, not a configured production identity provider.

The Task API supports GET /api/tasks, GET /api/tasks/{task_id}, POST /api/tasks, and POST /api/tasks/{task_id}/dry-run. Read and dry-run require task:read; creation requires task:create. There is no task execution or lifecycle mutation endpoint. Task IDs are generated by Core; explicit responses omit internal result/error fields. Dry-run previews routing without executing an Agent/Provider or changing Task state. See Documentation for endpoint details.

The Corporation dashboard is served at /ui; Employee Management is served at /ui/employees, and Provider & Model Management at /ui/providers. These pages use app-owned CSS and browser modules under /ui/static/, and call only existing protected APIs using same-origin credentials. Employee list/detail reads require employee:read; Employee create/delete require employee:manage. Provider reads require provider:read and create/delete require provider:manage; creation sends only Provider ID and name. Model assignment reads require model:read; replacements require model:manage and send only provider/model IDs for an Agent ID. The APIs expose no provider credentials/configuration and no Employee association for model assignments. Employee removal and Provider removal use explicit confirmation. No sign-in/session mechanism is configured, so unauthenticated requests show authentication-required states; 403 and other failures remain distinct. The pages do not access Core internals. The public Node.js documentation website in docs/ is an independent system.

Identity and execution concepts

Corporation is the identity of the modeled organization. Node identifies a participating installation and references its Corporation. RuntimeContext carries both IDs; the current initializer validates that the selected Node belongs to the selected Corporation. Local IDs are configured in code, and these registries are in-memory.

Employee is an organizational identity; Agent is a technical identity with capabilities and Provider/Model identifiers. Provider generates a response through its interface; Ollama is currently the only registered integration. Model is an identifier passed to the selected Provider. These concepts are deliberately separate.

Persistence and routing

SQLite currently stores Tasks, Projects, task logs, Agent memory, and project memory. Role and capability routing requirements are persisted on Tasks. A known gap is that TaskRegistry does not persist or reload project_id. Administrative registries for Employees, Agents, Providers, Corporation, and Node are not complete durable subsystems.

  1. Resolve an explicit assigned Agent.
  2. Otherwise resolve an exact Employee role match to its associated Agent.
  3. Otherwise match a required capability to an Agent.
  4. If no suitable Agent exists, report a routing failure; there is no automatic fallback.

Routing is deterministic, not AI/LLM-based. Dry-run inspects a route without invoking the Provider or mutating Task state.
