API boundary

The CLI also uses CorporationApplicationService. FastAPI provides Corporation status, Employee/Agent, Provider/Model assignment, Task, Project, and read-only Activity resources. Resource routes call the service, which delegates to the existing Core; routes do not access registries or logging storage directly. The default authentication backend rejects requests until an application supplies one. Protected resources check their declared permissions; this is an injectable security foundation, not a configured production identity provider.

The Task API supports GET /api/tasks, GET /api/tasks/{task_id}, POST /api/tasks, and POST /api/tasks/{task_id}/dry-run. Read and dry-run require task:read; creation requires task:create. There is no Task DELETE route or lifecycle mutation endpoint. Task IDs are generated by Core; explicit responses omit internal result/error fields. Dry-run previews routing without executing an Agent/Provider or changing Task state. Creation accepts title, description, optional project ID, and at most one Agent ID, role, or capability selector. See Documentation for endpoint details.

The Corporation dashboard is served at /ui; Employee Management is served at /ui/employees, Provider & Model Management at /ui/providers, Task Management at /ui/tasks, Project Management at /ui/projects, and Activity / Logs at /ui/activity. These pages use app-owned CSS and browser modules under /ui/static/, and call only existing protected APIs using same-origin credentials. Employee list/detail reads require employee:read; Employee create/delete require employee:manage. Provider reads require provider:read and create/delete require provider:manage; creation sends only Provider ID and name. Model assignment reads require model:read; replacements require model:manage and send only provider/model IDs for an Agent ID. Task list/detail/dry-run require task:read, and Task creation requires task:create. Project list/detail reads require project:read; Project creation requires project:create and sends only name and optional description. Activity reads use GET /api/activity with activity:read, optional supported limit (1–100) and task_id parameters, and display only the returned ID, Task ID, event, and timestamp fields. Activity is bounded, does not represent complete history, and has no detail endpoint. The API generates Project ID and status and exposes no Project deletion or lifecycle endpoint. The APIs expose no provider credentials/configuration and no Employee association for model assignments. Employee and Provider removal use explicit confirmation; Task and Project deletion are not exposed because their APIs do not support it. Default API mode has no configured sign-in/session backend and rejects unauthenticated requests. Explicit local-owner mode adds loopback login, scoped reads and chat; management permissions remain denied. Unauthenticated, forbidden and other failures remain distinct. The pages do not access Core internals. The public Node.js documentation website in docs/ is an independent system.

Documentation Portal — Task 53

The internal read-only page at /ui/documentation uses the protected GET /api/documentation list and GET /api/documentation/{document_id} detail routes; both require documentation:read and call the Documentation Application Service. Its replaceable default source reads only regular, top-level UTF-8 Markdown files from repository-root corporation_docs/. Document IDs are validated filename stems; resolved files must remain under the configured root, and symlink targets are rejected. The UI renders Markdown as text and does not read files, registries, or SQLite. This curated file-backed portal is not an AI-managed Knowledge System and is separate from this public docs/ website.

Updates / Changelog — Task 54

The internal read-only page at /ui/updates consumes protected GET /api/updates, requiring updates:read. Its replaceable Updates Application Service reads a fixed repository-root corporation_updates.json manifest with validated date, type, title, and summary fields. Entries are maintained manually for verified development changes or releases; versions and dates are not inferred from Git history. The browser clears stale results on failed refresh and does not access the filesystem directly. This internal curated source is separate from the public milestone summary in this documentation site's updates.html.

Conversation Foundation — Task 55

The Core defines in-memory Conversation and Message records with explicit open/closed conversation status and pending/completed/failed message status. Messages transition only from pending to a terminal result; closed conversations reject new messages, and conversations cannot close while messages remain pending. This foundation has no persistence, API/UI, provider interaction, Employee targeting, context retrieval, or Task creation/execution path. Future chat and task-handoff work remains separate.

Identity and execution concepts

Corporation is the identity of the modeled organization. Node identifies a participating installation and references its Corporation. RuntimeContext carries both IDs; the current initializer validates that the selected Node belongs to the selected Corporation. Local IDs are configured in code, and these registries are in-memory.

Employee is an organizational identity; Agent is a technical identity with capabilities and Provider/Model identifiers. Provider generates a response through its interface; Ollama is currently the only registered integration. Model is an identifier passed to the selected Provider. These concepts are deliberately separate.

System Monitoring — Task 75

CorporationApplicationService.monitor_system() assembles a fresh, on-demand immutable report from current Task status, Provider registration, and configured local resource-capacity snapshots. It reports failed Task IDs (bounded to 100 with an omitted count) and configured exhausted capacities as factual signals, not ranked alerts or policy thresholds. Provider availability remains UNKNOWN because monitoring never calls Providers; hardware feasibility remains unknown. If resource limits have not been configured, capacity observations are absent rather than fabricated. The report omits Task error text; independently sampled sources can change while it is collected, and it reserves no capacity. It does not persist or cache observations, execute Tasks, change assignments, schedule polling, or apply remediation. It adds no API/UI.

Error Detection — Task 76

New routing and execution-stage Task failures persist a structured category; historical failures without a category remain UNKNOWN. CorporationApplicationService.detect_failures() returns at most 100 failure summaries with Task IDs and category codes, reporting total and omitted counts. It never returns Task.error or exception/log message text. The categories identify the stage where failure was caught, not a root-cause diagnosis; no Provider retry, task execution, lifecycle change, or API/UI is added.

Diagnostic Agent — Task 77

CorporationApplicationService.diagnose_failure() makes exactly one call through the caller-selected registered Agent over 1–20 explicitly supplied sanitized evidence items, bounded to 32 KiB in total. Evidence references are opaque bounded IDs; the validated structured report only accepts citations matching IDs supplied in that request. It rejects stale failure records, malformed/oversized responses, and citations to missing evidence. No Task.error, logs, other records, or evidence sources are automatically retrieved. Results are in-memory and may be incorrect; citations establish reference identity, not that a claim is true. It creates/executes no Tasks, changes no assignments, retries nothing, and performs no remediation or API/UI work.

Maintenance Proposals — Task 78

CorporationApplicationService.create_maintenance_proposal() records caller-authored, immutable, in-memory proposals linked to an existing Task 77 diagnostic. Title, proposed change, scope, and risk are explicit and bounded caller inputs, not Agent-verified claims. Duplicate IDs are rejected; list/get are local and no persistence is added. Proposals do not alter Tasks, Agents, Providers, or source files. Task 79 adds a separate caller-supplied diff workflow; Task 83 adds human approval of exact maintenance workspaces, and Task 84 records approved changes as local Git checkpoints.

Automated Patch Development — Task 79

CorporationApplicationService.develop_patch() accepts a caller-supplied unified diff and an explicit list of existing UTF-8 source files under a caller-selected trusted repository root. It validates bounded paths, patch size, file sizes, hunk positions, and source context, then copies only the selected files into a temporary directory and applies the diff there. The immutable workspace snapshot records selected/changed files and source/patch digests; callers explicitly dispose of the temporary workspace. This temporary copy is not a security sandbox: the service executes no source, tests, scripts, Provider calls, Tasks, or Git operations, and changes no source files, assignments, or Task state. File additions/deletions/renames are unsupported.

Automated Testing Workflow — Task 80

CorporationApplicationService.run_selected_tests() accepts only explicitly selected Python test files that were copied into a registered Task 79 workspace. It clones only that workspace's selected files into a separate temporary directory and launches python -m pytest with an argument list (no shell), a fixed 120-second process timeout, a 64 KiB combined-output cap, no dependency installation or automatic pytest plugin loading, and a reduced environment with temporary/home locations redirected into the test copy. The immutable result reports the proposal/workspace IDs, selected tests, actual pytest exit code, bounded output, timestamps, and PASSED, FAILED, NO_TESTS, TIMED_OUT, or ERROR status; no result is persisted. The disposable directory and reduced environment are not an OS security sandbox: test code can still execute with the current user's host permissions. No Provider, Task, assignment, or resource-admission operation is invoked. Task 82 adds a separate Docker-only path.

Automated Code Review — Task 81

CorporationApplicationService.review_proposed_changes() makes exactly one call through the explicitly selected registered Agent, using only 1–20 caller-supplied sanitized DiagnosticEvidence items bounded to 32 KiB total. Supplied content is sent to the selected Agent's configured Provider; callers must sanitize the evidence and authorize its disclosure. The immutable in-memory report classifies findings by severity and review area and validates citations against supplied reference IDs, and includes a SHA-256 digest of the exact evidence tuple for later Task 85 linkage. No files, workspace, Task state, logs, or test results are retrieved automatically. Findings are advisory and may be incorrect; an empty findings list is not approval. The operation executes no tests or Tasks, changes no patches or assignments, changes no proposal/approval state, persists no result, and adds no API/UI. Task 83 adds the in-memory approval workflow; Task 84 adds a separately authorized local checkpoint operation.

Maintenance Sandbox — Task 82

CorporationApplicationService.run_sandboxed_tests() accepts only selected Python tests already in a registered Task 79 workspace and transfers the bounded files through Docker's archive API into a temporary writable, noexec tmpfs. It requires an explicitly allowed, locally present immutable image digest; no image pull is attempted. The container is non-root, has no host mounts, network, injected credentials, or writable root filesystem, drops all capabilities, applies process/memory/storage bounds, and is removed after execution. Test runtime is at most 60 seconds and combined output is capped at 64 KiB; the immutable actual-result report is in-memory only. Missing Docker, image, or controls blocks without falling back to Task 80's host-permission runner. The image and Docker daemon must be trusted; this does not defend against a compromised daemon or host administrator. Task 80 remains unchanged, and no Task, Agent assignment, provider, or API/UI behavior is involved. Task 83 adds a separate human approval workflow; Task 84 is a separate local checkpoint boundary.

Human Approval Workflow — Task 83

CorporationApplicationService.request_maintenance_approval() creates a bounded in-memory review request for a registered Task 79 workspace and presents the exact unified diff, changed files, and patch/source SHA-256 digests. Authenticated reviewers use /api/maintenance/approvals with maintenance:approve; the configured auth backend must grant that permission only to human reviewers. Approval/rejection records the principal identity and UTC decision time and is one-way from PENDING; decision submissions must echo both hashes. Approval binds to the same still-registered workspace and hash pair; require_approved_maintenance_workspace() exposes a fail-closed check for later consumers. The default auth backend rejects requests; decisions are in-memory and capped at 100. This workflow applies no patch, runs no Git operation, and executes no Task.

Git Checkpoint Integration — Task 84

CorporationApplicationService.create_maintenance_checkpoint() records only a still-registered Task 79 workspace with exact Task 83 approval. The authenticated /api/maintenance/checkpoints API requires the separate maintenance:checkpoint permission and records the caller identity in the report and local commit message. The service revalidates source/patch hashes, requires selected tracked regular files and a clean repository, then creates a commit on maintenance-checkpoints/<workspace-id> using a temporary Git index. It does not alter or switch the active worktree/index, push, merge, execute Tasks, or change assignments/resources. Branches and commits persist locally; API reports are in-memory. Recovery after later integration is an explicit git revert; Task 85 records existing results but does not perform these operations.

Controlled Self-Maintenance — Task 85

CorporationApplicationService.start_maintenance_workflow() and its record methods maintain a bounded caller-driven progression from an existing Task 76 failure: Task 77 diagnostic, Task 78 proposal, Task 79 workspace, one Task 80/82 test report, then Task 81 review. The review report binds a SHA-256 digest to the exact supplied evidence, which must include the workspace diff. A PASSED test and recorded review make the workflow eligible for Task 83 approval; review findings remain advisory. Pending/final Task 83 decisions and Task 84 checkpoints are separately performed by their existing services and only recorded after workspace/hash checks. Task 85 does not call Providers, run tests, request/decide approvals, create checkpoints, apply patches, create/execute Tasks, or change assignments/resources. Failed tests terminate the workflow; there are no automatic retries or background stages. Immutable snapshots are in-memory (maximum 100 workflows, nine events each), while metadata-only stage events use existing Task logs. No API/UI or new database schema is added; workflow state cannot resume after restart. Task 70 controlled execution/admission, Task 71 resource awareness, Task 72 provider availability, and Task 73 review-only candidate selection remain unchanged; Task 85 makes no routing or candidate-selection decision. Task 87 is documented separately below; The Task 87 description is historical; see the shared task contracts for current completion and limitations.

Task 86 MCP Integration

The opt-in MCPToolClient connects only to explicitly configured local stdio or in-process MCP servers. A frozen tool-name allowlist controls discovery; callers explicitly register selected tools into ToolRegistry and invoke them through the existing synchronous Tool.execute() contract. Calls have a bounded timeout and bounded JSON inputs and text/structured results, and server/protocol errors are sanitized. Custom child-process environments are rejected; local MCP servers still run with host permissions and are not OS-sandboxed. The adapter is not wired to Agents, Tasks, APIs, or UI; it creates no Tasks, invokes no Agent, and has no background discovery or polling or application-level retry loops. It adds no credentials, network transport, or GitHub workflow; Task 87 is documented separately below.

GitHub Integration — Task 87

The authenticated GET /api/github/repositories/{owner}/{repository} route requires github:read and delegates through GitHubRepositoryInspectionService to Task 27 public repository discovery. Each application instance must receive an explicit immutable set of GitHubRepositoryScope entries; the default scope is empty. Out-of-scope, missing, and private repositories are indistinguishable to callers, and an out-of-scope request never contacts GitHub. The response contains selected public metadata but omits README content. This is read-only: there are no credentials, private-repository access, branch/commit/pull-request writes, Task/Agent calls, or approval records. The github:read permission and exact repository allowlist are the confirmed access gates. At Task 87 completion, Tasks 88–100 remained planned.

Browser/Web Research — Task 88

WebResearchClient retrieves one caller-supplied page URL per explicit call from an immutable exact-host allowlist, empty by default. It accepts HTTPS without credentials, query strings, fragments, or non-default ports, disables environment proxies and redirects, and does not search, crawl, or follow links. Requests time out after 10 seconds; response bodies are limited to 512 KiB and extracted text to 20,000 characters. HTML/plain-text results are immutable and classified as untrusted evidence; instruction-like content remains data and is not sent to Agents or Providers. There is no API/UI, persistence, browser automation, Task execution, or background polling. At Task 88 completion, Tasks 89–100 remained planned.

Coding Tool Integration — Task 89

CodingToolProposalService invokes one explicitly selected, registered MCPTool. The tool must accept an instruction and caller-selected path/content pairs and return a unified diff. Inputs are limited to 16 KiB, eight files, and 4 KiB per file; returned diffs are limited to 65,536 bytes and 10,000 lines and may modify only selected paths. The immutable result binds source and patch digests. Task 89 does not apply the diff, execute code, create a workspace, run tests, or invoke review; Task 79 and Tasks 80/81 remain separate caller actions. MCP servers remain trusted local processes with host permissions, not OS sandboxes. No Agent/Provider call, Task creation/execution, persistence, API/UI, or automatic retry is added. The Task 89 description is historical; see the shared task contracts for current completion and limitations.

Persistence and routing

SQLite currently stores Tasks, Projects, task logs, Agent memory, and project memory. Role and capability routing requirements are persisted on Tasks. Task 63 added Task project_id persistence and reload. Historical rows without an association remain unlinked; no historical project relationship is inferred. Administrative registries for Employees, Agents, Providers, Corporation, and Node are not complete durable subsystems.

  1. Resolve an explicit assigned Agent.
  2. Otherwise resolve an exact Employee role match to its associated Agent.
  3. Otherwise match a required capability to an Agent.
  4. If no suitable Agent exists, report a routing failure; there is no automatic fallback.

Routing is deterministic, not AI/LLM-based. Dry-run inspects a route without invoking the Provider or mutating Task state.

Capability Registry — Task 92

CapabilityRegistry is a read-only, in-memory aggregation of existing Agent-declared capability strings, ToolRegistry entries, the scope-only IntegrationCapability enum, and an optional caller-supplied Gemini catalog snapshot. Evidence status distinguishes declarations, registrations, possible scopes, and service-reported metadata. Owner fields identify the source component/Agent/Tool or model, not a human authorization principal. Requirements remain unknown where a source does not declare them. A supplied Gemini snapshot's timestamp, model count, and pagination completeness are preserved; models without allowlisted method metadata do not create inferred capability entries, and the registry makes no API call. Records are immutable, stably ordered, bounded to 2,000, and describe policy limits without granting access, verifying expertise, executing Tools, or guaranteeing service/model execution. Registry reads are sequential, not an atomic cross-source transaction. No persistence, API/UI, background refresh, assignment change, routing, or Task execution is added. Context Retrieval — Task 66

Added bounded deterministic Context Retrieval over explicitly selected authorized memory scopes, with source references, provenance, expiry and revision traces, live scoped access rechecks, and explicit candidate/result/byte limit indicators.

ContextRetrievalService is available through application_service.context_retrieval(). Trusted callers supply the authenticated actor, one exact conversation/project/Corporation scope, a timezone-aware current time, and a keyword query. It uses case-folded word matching, ranks by distinct matched terms with memory-ID tie breaking, and does not broaden access or scope. Queries are limited to 1024 UTF-8 bytes and 32 distinct terms; retrieval scans at most 100 authorized records, returns at most 10 matches (default 5), and bounds serialized hit payloads to 32768 bytes. Candidate-limit reporting is conservative when exactly 100 records are returned; results are not a complete-history or semantic-search guarantee. Expired records are excluded, project associations are verified, named-reader grants are rechecked, and corrupt data fails explicitly. Immutable results carry original references, expiry, and revision; caller-held snapshots cannot be revoked and must be retrieved again before later use.
