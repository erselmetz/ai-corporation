API boundary

The CLI also uses CorporationApplicationService. FastAPI provides Corporation status, Employee/Agent, Provider/Model assignment, Task, Project, and read-only Activity resources. Resource routes call the service, which delegates to the existing Core; routes do not access registries or logging storage directly. The default authentication backend rejects requests until an application supplies one. Protected resources check their declared permissions; this is an injectable security foundation, not a configured production identity provider.

The Task API supports GET /api/tasks, GET /api/tasks/{task_id}, POST /api/tasks, and POST /api/tasks/{task_id}/dry-run. Read and dry-run require task:read; creation requires task:create. There is no Task DELETE route or lifecycle mutation endpoint. Task IDs are generated by Core; explicit responses omit internal result/error fields. Dry-run previews routing without executing an Agent/Provider or changing Task state. Creation accepts title, description, optional project ID, and at most one Agent ID, role, or capability selector. See Documentation for endpoint details.

The Corporation dashboard is served at /ui; Employee Management is served at /ui/employees, Provider & Model Management at /ui/providers, Task Management at /ui/tasks, Project Management at /ui/projects, and Activity / Logs at /ui/activity. These pages use app-owned CSS and browser modules under /ui/static/, and call only existing protected APIs using same-origin credentials. Employee list/detail reads require employee:read; Employee create/delete require employee:manage. Provider reads require provider:read and create/delete require provider:manage; creation sends only Provider ID and name. Model assignment reads require model:read; replacements require model:manage and send only provider/model IDs for an Agent ID. Task list/detail/dry-run require task:read, and Task creation requires task:create. Project list/detail reads require project:read; Project creation requires project:create and sends only name and optional description. Activity reads use GET /api/activity with activity:read, optional supported limit (1–100) and task_id parameters, and display only the returned ID, Task ID, event, and timestamp fields. Activity is bounded, does not represent complete history, and has no detail endpoint. The API generates Project ID and status and exposes no Project deletion or lifecycle endpoint. The APIs expose no provider credentials/configuration and no Employee association for model assignments. Employee and Provider removal use explicit confirmation; Task and Project deletion are not exposed because their APIs do not support it. No sign-in/session mechanism is configured, so unauthenticated requests show authentication-required states; 403 and other failures remain distinct. The pages do not access Core internals. The public Node.js documentation website in docs/ is an independent system.

Documentation Portal — Task 53

The internal read-only page at /ui/documentation uses the protected GET /api/documentation list and GET /api/documentation/{document_id} detail routes; both require documentation:read and call the Documentation Application Service. Its replaceable default source reads only regular, top-level UTF-8 Markdown files from repository-root corporation_docs/. Document IDs are validated filename stems; resolved files must remain under the configured root, and symlink targets are rejected. The UI renders Markdown as text and does not read files, registries, or SQLite. This curated file-backed portal is not an AI-managed Knowledge System and is separate from this public docs/ website.

Updates / Changelog — Task 54

The internal read-only page at /ui/updates consumes protected GET /api/updates, requiring updates:read. Its replaceable Updates Application Service reads a fixed repository-root corporation_updates.json manifest with validated date, type, title, and summary fields. Entries are maintained manually for verified development changes or releases; versions and dates are not inferred from Git history. The browser clears stale results on failed refresh and does not access the filesystem directly. This internal curated source is separate from the public milestone summary in this documentation site's updates.html.

Conversation Foundation — Task 55

The Core defines in-memory Conversation and Message records with explicit open/closed conversation status and pending/completed/failed message status. Messages transition only from pending to a terminal result; closed conversations reject new messages, and conversations cannot close while messages remain pending. This foundation has no persistence, API/UI, provider interaction, Employee targeting, context retrieval, or Task creation/execution path. Future chat and task-handoff work remains separate.

Identity and execution concepts

Corporation is the identity of the modeled organization. Node identifies a participating installation and references its Corporation. RuntimeContext carries both IDs; the current initializer validates that the selected Node belongs to the selected Corporation. Local IDs are configured in code, and these registries are in-memory.

Employee is an organizational identity; Agent is a technical identity with capabilities and Provider/Model identifiers. Provider generates a response through its interface; Ollama is currently the only registered integration. Model is an identifier passed to the selected Provider. These concepts are deliberately separate.

Persistence and routing

SQLite currently stores Tasks, Projects, task logs, Agent memory, and project memory. Role and capability routing requirements are persisted on Tasks. A known gap is that TaskRegistry does not persist or reload project_id. Administrative registries for Employees, Agents, Providers, Corporation, and Node are not complete durable subsystems.

  1. Resolve an explicit assigned Agent.
  2. Otherwise resolve an exact Employee role match to its associated Agent.
  3. Otherwise match a required capability to an Agent.
  4. If no suitable Agent exists, report a routing failure; there is no automatic fallback.

Routing is deterministic, not AI/LLM-based. Dry-run inspects a route without invoking the Provider or mutating Task state.

Integration boundary

Tasks 26–36 establish an in-memory proposal and source pipeline: public GitHub discovery, bounded analysis, evidence-based evaluation and proposal generation, sandbox/executor boundaries, optional Docker execution, inert source staging, integrity-checked binding, and execution preparation. Preparation does not execute code. See Integrations for details.

The documentation website lives in this repository's docs/ folder. Its Node.js server serves documentation assets only; it does not import the Python app or connect to runtime services.

Individual Employee Chat — Task 56

The in-memory Core EmployeeChatService accepts exactly one explicit Employee or Agent selection. An Employee must have an assigned, registered Agent. Conversation targets capture fixed Employee/Agent IDs and employee or agent scope; later Employee reassignment does not retarget existing conversations. Callers explicitly record ordered messages and pending → completed or failed outcomes, using Task 55 lifecycle rules. Immutable snapshots prevent callers from modifying the service-owned records. There is no automatic response generation, provider interaction, context retrieval, persistence, Conversation API/UI, Orchestrator coordination, or Task creation/execution.

Chat Context — Task 57

Added caller-supplied context bounded to 8192 UTF-8 bytes per conversation, with atomic replacement, isolation, and clearing on successful closure; no retrieval, persistence, provider calls, or chat API/UI. Trusted Core callers enforce authorization and relevance before supplying text; caller-held copies cannot be revoked. The Documentation Portal remains file-based and read-only.

Corporation Chat — Task 58

Added local Corporation Chat CLI commands with explicit coordinator Agent identity, Orchestrator-mediated replies, bounded prompts, isolated conversation history, and recorded response failures; no automatic Task creation or Web/API chat. Local chat is trusted and in-memory; explicit sends may call the configured provider, while tests use fakes. The file-based Documentation Portal is unchanged.

Corporation Task Creation via Chat — Task 59

Added immutable chat-to-Task reviews of completed user messages with explicit project and Agent routing; human CONFIRM creates a pending persisted Task without execution, and consumed reviews cannot be replayed. Reviews and local human confirmation are separate from sending chat messages. Review state is in-memory; uncertain creation failures require human inspection.

AI Activity Visualization — Task 60

Added permission-aware Task lifecycle progress to the Activity page using protected Task detail reads, with explicit pending/running/completed/failed states, separate access errors, stale-response rejection, and no fabricated provider telemetry. Select a Task ID and refresh for a current lifecycle snapshot. task:read is checked independently of activity:read. Local chat has no browser telemetry.

Memory Architecture — Task 61

Defined immutable scoped memory records with explicit owners, note/summary types, required provenance and expiry, retention opt-in, and exact owner/scope retrieval checks without automatic sharing or storage. Trusted callers bind owner identity and validate sources. Existing legacy key-value stores remain separate. Persistent conversation notes are explicitly supported by Task 62; no automatic transcript archive is added.

Persistent Conversation Memory — Task 62

Added explicitly opted-in SQLite conversation memory with immutable bounded records, owner/conversation-scoped retrieval, expiry enforcement, explicit deletion and scoped cleanup, and corrupt-data rejection; chat messages are never saved automatically. Retained notes survive chat closure until expiry/deletion. Cleanup is explicit; SQLite is plaintext. No memory HTTP/UI interface or automatic transcript archive is added.

Project Knowledge — Task 63

Added private owner-scoped durable Project Knowledge with explicit Task provenance and verified project associations; reused retention/access rules and added non-destructive Task project-ID persistence without inferring historical links. Private knowledge requires consent, expiry, and matching Project/Task references. Historical Tasks lacking project associations cannot be linked automatically. No HTTP/UI knowledge interface is added.

Corporation Knowledge — Task 64

Added explicit owner-approved Corporation Knowledge publication to bounded named-reader lists, with copied provenance and inherited expiry, deny-by-default scoped reads, owner revocation/withdrawal, and atomic durable publication; private memory is never shared automatically. Publication is a separately consented immutable copy; its owner controls revocation. Private source deletion does not withdraw publication. No knowledge HTTP/UI route is added.

Memory Management UI — Task 65

Added authorized memory inspection, owner correction and explicit retention, revision-conflict protection, expired-record removal, and owner withdrawal of immutable published knowledge through scoped API services and a browser page; default authentication remains fail-closed.

The /ui/memory page uses protected /api/memory services. memory:read permits scoped inspection; memory:manage also requires record ownership for mutations. The server binds owners/readers to authenticated identity and denies access by default. Lists contain metadata only (50 records by default, maximum 100), including expired records whose content cannot be read or restored. Active private notes can be corrected or retained with explicit consent and a future timezone-aware expiry; source references remain intact and stale revisions are rejected. Published knowledge is an immutable snapshot: named readers can inspect it, while its owner can withdraw it. Removing a private source does not withdraw separately consented publication; deletion cannot revoke caller-held copies or backups. This page adds no automatic capture, provider execution, semantic retrieval, or changes to the file-based read-only Documentation Portal. Browser authentication remains unconfigured.
