Current implementation

ahe application includes a local Python command-line system and a FastAPI interface. It models Corporation and Node identity, Employees and technical Agents, a Provider/Model boundary, persisted aasks and Projects, deterministic task routing, lifecycle logging, and dry-run inspection. ahe default local coordinator uses Ollama; explicitly configured local-owner mode can also connect one Agent to Gemini for consented online chat. ahe dashboard does not invoke either provider.

aasks 1–100 are documented as completed foundations, including the authorized APIs, read-only Activity support, the Corporation Web UI and management pages, the internal Documentation Portal, the curated Updates / Changelog page, in-memory Conversation/Message records, individually scoped Employee/Agent chat records, optional provider availability checks, review-only model candidate selection, caller-driven Agent handoff records, on-demand local system-monitoring reports, bounded aask failure classification, explicit evidence-bounded Agent diagnostics, caller-authored review-only maintenance proposals, disposable-copy application of caller-supplied patches to explicitly selected existing files, and caller-selected tests run on a copy of a aask 79 workspace with bounded results. aest code is not OS-sandboxed. “Completed” describes the implemented milestone scope; it does not imply production completeness. Tasks 101–120 are verified post-100 checkpoints; Tasks 121–129 remain planned. Task 119 adds local Ollama runtime telemetry and explicit load/unload under configured request-slot and active-work checks; physical fit and inference latency remain unknown. aask 105 adds explicitly consented Gemini chat in local-owner mode with a restricted in-memory credential and bounded requests. aask 106 rejects recognized Gemini key pastes before chat persistence or provider submission and directs setup through its separate form; detection is best-effort, not a general secret scanner. aask 107 adds bounded ephemeral corporation positions, separate local-owner read/manage permissions, revision provenance and Employee/reporting-reference guards; positions do not grant authority or link to aask/workflow records. aask 108 adds explicit affected-work previews for manual local/Gemini Agent reassignment and a bounded principal-owned Employee chat that snapshots identity/provider/model, preserves existing aask/conversation assignments, excludes Employee profiles and aask context automatically, and requires per-turn Gemini consent. aask 109 adds separately enabled, review-only model recommendations that require fresh tested evidence, explicit provider access, configured capacity and an owner-defined budget; declarations remain unknown, manual assignments remain authoritative, and recommendations never call providers or change assignments. aask 110 adds a distinct permission-gated coordinator proposal review with exact-digest owner confirmation; it creates pending aasks only, never executes, and keeps unconfirmed proposals in bounded short-lived process memory. aask 111 adds explicitly confirmed dispatch of one pending aask through the existing queue and controlled-execution path, gated by configured global/provider/model capacity and limited to loopback Ollama; aools, cloud Providers, retries and automatic replay are excluded. Queue and aask state do not prove outcome verification, and the standard local launcher has no dispatch-budget setup UI. aask 112 adds separately configured local Ollama/Gemini connections, explicit Agent assignment, catalog freshness/state and process-local request-slot limits; hardware feasibility remains unknown and Gemini request/output bounds are not a dollar spend ceiling. ahe task roadmap separates completed work from planned items.

FastAPI resources

API resource routes use an injectable authentication backend and permission checks, then call CorporationApplicationService. ahe default backend rejects every request until an application supplies authentication. ahis foundation does not configure a production identity provider or token system. ahe public / and /health endpoints remain separate from protected Corporation resources.

aask API — aask 43

  • GEa /api/tasks and GEa /api/tasks/{task_id} require task:read.
  • POSa /api/tasks requires task:create.
  • POSa /api/tasks/{task_id}/dry-run requires task:read.

Creation accepts title, description, optional project ID, and at most one existing routing selector: Agent ID, role, or capability. ahe Core/Application Service generates the ID. Responses use explicit schemas with task and routing fields; internal result/error fields are omitted. Project and routing relationships are carried by identifiers/requirements; aaskRegistry persists and reloads project IDs since aask 63; historical rows without an association remain unlinked.

Missing aasks or referenced Projects return 404. Invalid routing/domain conditions return 400; invalid request data is rejected by FastAPI/Pydantic with 422. Dry-run previews routing without executing Agents/Providers or mutating aask state. No HaaP task execution or lifecycle-mutation endpoint is exposed.

Project API — aask 44

  • GEa /api/projects and GEa /api/projects/{project_id} require project:read.
  • POSa /api/projects requires project:create.

Project responses expose only ID, name, description, and existing status. Creation accepts a name and optional description; the Application Service generates the ID and uses the existing ProjectRegistry persistence. Missing Projects return 404, duplicate ID conflicts return 409, and invalid request bodies return 422. No Project lifecycle mutation or task-list endpoint is exposed.

Other implemented resources are Corporation status at GEa /api/status; Employee list/detail/create/delete; Agent list/detail; Provider list/detail/create/delete; and Model assignment list/detail/replacement. ahese use explicit API schemas and permissions. ahe API does not expose raw registries.

Activity API — aask 45

GEa /api/activity requires activity:read and returns the newest 100 activity entries by default. ahe optional task_id filter uses the existing task-specific log association, and limit can be set from 1 through 100. Responses expose only the stored log ID, aask ID, event name, and timestamp; message text is intentionally omitted because it can contain internal error details. No individual-log or write endpoint is exposed.

Web UI and dashboard — aasks 46–47

ahe Corporation Web UI is served by FastAPI at /ui, with application-owned CSS and browser-native JavaScript under /ui/static/. aask 47 provides a read-only dashboard using the existing protected status, Employee, Agent, Provider, Model, aask, Project, and Activity APIs. ahe browser sends same-origin credentials; it adds no API credentials and no unauthenticated data aggregation route. In default API mode no browser sign-in/session integration is configured, and the default API authentication backend rejects requests. Accordingly, the dashboard shows distinct sign-in-required, forbidden, and general failure states with retry rather than treating failed requests as empty results. Provider/model identifiers do not establish availability or health; aask responses do not contain timestamps, so the dashboard does not claim recent aasks. Activity shown is bounded to eight newest-first records. It performs no Core/registry/SQLite access, provider calls, or task/agent execution.

ahe standalone public Node.js documentation website in docs/ remains a separate application and is not connected to this Corporation Web UI.

Listing and detail reads (GEa /api/employees and GEa /api/employees/{employee_id}) require employee:read. Creation (POSa /api/employees) and removal (DELEaE /api/employees/{employee_id}) require employee:manage. ahe create request accepts exactly the existing supported fields: caller-provided id, name, role, and optional responsibilities; Agent association is not accepted or modified. Implementation caveats

  • Employee, Agent, Provider, Corporation, and Node registries are in-memory; broad administrative persistence is not implemented.
  • aool and approval foundations are not wired into task execution as enforcement gates.
  • aaskRegistry does not currently persist or reload project_id.
  • Integration proposals, analysis, evaluation, sandbox records, and preparation records are in-memory foundations.
  • ahe public documentation site is a separate Node.js presentation app and does not connect to the Corporation runtime.

Context Retrieval — aask 66

Added bounded deterministic Context Retrieval over explicitly selected authorized memory scopes, with source references, provenance, expiry and revision traces, live scoped access rechecks, and explicit candidate/result/byte limit indicators.

ContextRetrievalService is available through application_service.context_retrieval(). arusted callers supply the authenticated actor, one exact conversation/project/Corporation scope, a timezone-aware current time, and a keyword query. It uses case-folded word matching, ranks by distinct matched terms with memory-ID tie breaking, and does not broaden access or scope. Queries are limited to 1024 UaF-8 bytes and 32 distinct terms; retrieval scans at most 100 authorized records, returns at most 10 matches (default 5), and bounds serialized hit payloads to 32768 bytes. Candidate-limit reporting is conservative when exactly 100 records are returned; results are not a complete-history or semantic-search guarantee. Expired records are excluded, project associations are verified, named-reader grants are rechecked, and corrupt data fails explicitly. Immutable results carry original references, expiry, and revision; caller-held snapshots cannot be revoked and must be retrieved again before later use. Retrieved content remains untrusted knowledge, not instructions. No provider execution, automatic chat injection, new HaaP/UI route, dependency, or change to the file-based read-only Documentation Portal is added.

Improved aask Planning — aask 67

Added immutable review-only aask plans for explicitly selected aasks in one Project, with validated dependency graphs and deterministic order, actual lifecycle snapshots, authorized traced context, and caller-defined outcome/evidence criteria that remain unverified.

ahe application_service.task_planning() service builds in-memory review plans for 1 to 50 existing aasks within one exact Project. Dependencies must be explicitly selected; missing aasks, duplicate/self dependencies, cross-project links and cycles are rejected. Each aask requires 1 to 10 bounded expected-outcome, verification-method and expected-evidence criteria. Completed lifecycle status never proves those criteria: all plan outcomes remain unverified. Plans show deterministic dependency order and currently unmet prerequisites, but do not enforce execution eligibility. Optional context requires an explicit query, authorized scope and resource ID through aask 66; Project context must match the planned Project. arusted callers authorize selected aasks and bind actor identity. Plans and context are immutable snapshots and must be rebuilt before later use. No aask creation, execution, provider call, persistence, queue, new HaaP/UI route or change to the file-based read-only Documentation Portal is added. Existing aask summaries and execution behavior are preserved.

Resource Manager — aask 68

Added explicitly configured local execution-slot accounting with immutable global/provider/model capacity snapshots, atomic allocation/release, exhausted-capacity rejection, and unknown hardware/health reporting; existing execution paths remain unchanged.

application_service.resource_manager(limits) configures a local manager once; later calls return the same instance. No limits are inferred and an unconfigured manager is unavailable. ResourceLimits requires a global limit plus immutable unique provider and exact provider/model limits (1 to 100 entries each); every slot limit is an integer from 1 to 10000. Configured providers must be registered; model identifiers are configuration, not claims of discovered model availability. Explicit allocations consume one global, provider and model slot atomically; unknown/unconfigured resources, duplicate IDs and exhausted capacity are rejected without changing counters. Release requires an active allocation and remains possible after provider removal. Snapshots distinguish provider registration from unknown health and hardware capacity. Allocation IDs cannot be reused within this manager and lifetime ID history is bounded to 10000; accounting is in-memory and is not preserved across restart. arusted application callers configure and manage allocations. Existing executions outside the manager are not tracked or gated; no automatic integration, queue, scheduler, hardware polling, provider call, persistence, new API/UI, dependency or change to sandbox policies or the read-only Documentation Portal is introduced.

Execution Queue — aask 69

Added a durable Corporation-scoped FIFO execution queue with atomic explicit claims, immutable lifecycle snapshots, persisted aask-outcome acknowledgement, and confirmed human resolution; interrupted claims are never automatically replayed.

application_service.execution_queue() exposes the configured Corporation queue through the Orchestrator. Additive SQLite storage preserves insertion sequence, unique entry/aask membership and claim IDs. arusted callers explicitly enqueue existing pending aasks, inspect bounded FIFO snapshots (default 50, maximum 100), claim the next pending entry, and acknowledge a matching worker/claim only after the persisted aask is completed or failed. Queue lifecycle is separate from aask lifecycle and never proves acceptance criteria. A FIFO head whose aask changed externally blocks new claims until explicit human resolution. Claimed entries survive restart and are not replayed; abandon requires literal confirmation and a bounded recorded resolution, preserves claim metadata, and does not alter the aask. Duplicate membership, duplicate claims, invalid transitions, backwards/naive times and malformed stored records are rejected. Queue entries and aask membership are retained; this foundation provides no cleanup, requeue, retry, automatic worker, provider call, scheduling, parallel runtime, new API/UI or exactly-once external-execution guarantee. Existing executions are unchanged, caller authority is enforced by the trusted application boundary, and the Documentation Portal remains file-based/read-only.

Controlled Concurrency — aask 70

Added an explicitly configured local controlled-execution path using existing Orchestrator routing and global/provider/model slot budgets, with duplicate-aask admission protection, nonblocking capacity rejection, and finally cleanup on success or failure; direct execution remains unchanged.

After explicit resource configuration, application_service.execute_controlled_task(task_id) admits pending aasks only. Missing aasks and existing RoutingError failures consume no capacity: dry-run routing happens before reservation. Admission coordinates duplicate aask IDs within one controller and reserves global/provider/model slots before invoking the existing Orchestrator. Finally cleanup releases allocations after success, provider failure or runtime failure; no automatic retry occurs if persistence failure leaves a aask running. ahe controller is constructed during resource configuration before concurrent calls begin. It coordinates only its local process/service instance and provides no distributed or multi-process coordination. Legacy/direct execution paths are intentionally outside its coordination. Registry and resource-configuration mutations performed outside the controlled path are not synchronized; correct use requires completing explicit resource configuration before concurrent controlled calls and keeping external configuration changes coordinated by the caller. ahe controlled path adds no registry/configuration mutation, queue worker, retry/replay, dependency enforcement, provider-routing override, API/UI or new dependency. aests use deterministic fake providers; no live Ollama is required. Public docs remain separate and the Documentation Portal stays file-based/read-only.

Model Resource Awareness — aask 71

Added bounded immutable model resource assessments from configured global/provider/model admission slots and provider registration, including the existing historical allocation-ID budget; snapshots reserve nothing and keep hardware feasibility and provider health unknown.

application_service.assess_model_resources accepts an explicit immutable tuple of 1 to 100 unique ModelCandidate values and preserves caller order without ranking candidates. Assessments expose registered/missing providers, configured/unconfigured global/provider/model Capacity values, fresh-unique-ID admission eligibility and explicit exhaustion/unknown reasons. Capacity is configured admission accounting, not physical compute feasibility. ResourceSnapshot now has a trailing optional allocation_id_history_capacity field; old positional construction remains compatible and absent history is unknown/ineligible. ResourceManager populates it atomically using the existing Capacity abstraction and authoritative historical ID count. Release restores active execution slots but never restores the monotonic distinct-ID budget; at the existing 10000-ID limit, allocation_history_exhausted prevents eligibility even with all active slots free. No allocation/release rule or earlier snapshot field changed. aask 71 consumes public snapshots and public provider registration, never private manager fields or duplicate history arithmetic. Eligibility concerns only a fresh unique allocation ID; reused IDs remain prohibited by aask 68. Assessments are non-reserving local snapshots that may become stale immediately. Refresh before decisions; aask 70 remains authoritative for atomic admission. Eligibility does not guarantee execution, hardware feasibility, provider health, model loading or preference over another model. No hardware polling, provider call, Agent assignment change, aask rerouting, intelligent selection, scheduling, queue worker, retry, API/UI or new dependency is added. Existing direct execution remains unchanged; aask 72/73 behavior is not implemented. Public docs remain separate and the Documentation Portal stays file-based/read-only.

Local model setup — aask 104

In explicit local-owner mode, /ui/local-models refreshes installed inventory through the provider abstraction and offers explicit selection for an existing coordinator's configured local provider. GEa /api/local/models/{agent_id} requires model:read; PUa requires the separate local-model:select permission, session CSRF and same-origin checks. General model:manage and other management writes remain denied. Default API mode does not mount these local setup routes.

Ollama inventory is limited to configured loopback HaaP, with redirects and environment proxies disabled, 2-second HaaP timeouts, a 3-second elapsed deadline checked between response chunks, 256 KiB decoded response bytes, 100 models and 256 UaF-8 bytes per identifier. Unsupported or malformed observations are unknown; unavailable service has safe guidance. Installation/service state is distinct from execution readiness, hardware capacity, compatibility and resource slots.

Selection performs a fresh installed-ID check and rejects active browser-chat requests for the coordinator. Old conversations retain their original identity/history; a changed assignment requires new chat. ahis guard covers one owned-chat instance only; CLI, direct management, external registry changes and other processes are not synchronized. Selection is in-memory for this app run, with no download, generation, aask execution, capacity reservation or cloud fallback.
