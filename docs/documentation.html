Documentation

A guide to the Corporation's implemented foundations and documented direction.

Current implementation

The application includes a local Python command-line system and a FastAPI interface. It models Corporation and Node identity, Employees and technical Agents, a Provider/Model boundary, persisted Tasks and Projects, deterministic task routing, lifecycle logging, and dry-run inspection. The current runtime uses Ollama for provider execution; the dashboard does not invoke it.

Tasks 1–62 are documented as completed foundations, including the authorized APIs, read-only Activity support, the Corporation Web UI and management pages, the internal Documentation Portal, the curated Updates / Changelog page, in-memory Conversation/Message records, and individually scoped Employee/Agent chat records. “Completed” describes the implemented milestone scope; it does not imply production completeness. Tasks 63–100 remain planned. The task roadmap separates completed work from planned items.

FastAPI resources

API resource routes use an injectable authentication backend and permission checks, then call CorporationApplicationService. The default backend rejects every request until an application supplies authentication. This foundation does not configure a production identity provider or token system. The public / and /health endpoints remain separate from protected Corporation resources.

Task API — Task 43

  • GET /api/tasks and GET /api/tasks/{task_id} require task:read.
  • POST /api/tasks requires task:create.
  • POST /api/tasks/{task_id}/dry-run requires task:read.

Creation accepts title, description, optional project ID, and at most one existing routing selector: Agent ID, role, or capability. The Core/Application Service generates the ID. Responses use explicit schemas with task and routing fields; internal result/error fields are omitted. Project and routing relationships are carried by identifiers/requirements; the existing TaskRegistry does not persist or reload the project ID.

Missing Tasks or referenced Projects return 404. Invalid routing/domain conditions return 400; invalid request data is rejected by FastAPI/Pydantic with 422. Dry-run previews routing without executing Agents/Providers or mutating Task state. No HTTP task execution or lifecycle-mutation endpoint is exposed.

Project API — Task 44

  • GET /api/projects and GET /api/projects/{project_id} require project:read.
  • POST /api/projects requires project:create.

Project responses expose only ID, name, description, and existing status. Creation accepts a name and optional description; the Application Service generates the ID and uses the existing ProjectRegistry persistence. Missing Projects return 404, duplicate ID conflicts return 409, and invalid request bodies return 422. No Project lifecycle mutation or task-list endpoint is exposed.

Other implemented resources are Corporation status at GET /api/status; Employee list/detail/create/delete; Agent list/detail; Provider list/detail/create/delete; and Model assignment list/detail/replacement. These use explicit API schemas and permissions. The API does not expose raw registries.

Activity API — Task 45

GET /api/activity requires activity:read and returns the newest 100 activity entries by default. The optional task_id filter uses the existing task-specific log association, and limit can be set from 1 through 100. Responses expose only the stored log ID, Task ID, event name, and timestamp; message text is intentionally omitted because it can contain internal error details. No individual-log or write endpoint is exposed.

Web UI and dashboard — Tasks 46–47

The Corporation Web UI is served by FastAPI at /ui, with application-owned CSS and browser-native JavaScript under /ui/static/. Task 47 provides a read-only dashboard using the existing protected status, Employee, Agent, Provider, Model, Task, Project, and Activity APIs. The browser sends same-origin credentials; it adds no API credentials and no unauthenticated data aggregation route. No browser sign-in/session integration is configured, and the default API authentication backend rejects requests. Accordingly, the dashboard shows distinct sign-in-required, forbidden, and general failure states with retry rather than treating failed requests as empty results. Provider/model identifiers do not establish availability or health; Task responses do not contain timestamps, so the dashboard does not claim recent Tasks. Activity shown is bounded to eight newest-first records. It performs no Core/registry/SQLite access, provider calls, or task/agent execution.

The standalone public Node.js documentation website in docs/ remains a separate application and is not connected to this Corporation Web UI.

Employee Management — Task 48

The Employee Management page is served at /ui/employees, links back to the dashboard, and uses the existing /api/employees endpoints only. Listing and detail reads (GET /api/employees and GET /api/employees/{employee_id}) require employee:read. Creation (POST /api/employees) and removal (DELETE /api/employees/{employee_id}) require employee:manage. The create request accepts exactly the existing supported fields: caller-provided id, name, role, and optional responsibilities; Agent association is not accepted or modified. Removal requires explicit confirmation. The page presents authentication-required, forbidden, conflict, validation, missing-record, and general failure states. Browser sign-in/session authentication remains unconfigured, so protected data and actions require an authenticated session. The API itself calls CorporationApplicationService; the UI does not access registries or persistence directly.

Tasks 49–52 add Provider/Model, Task, Project, and Activity interfaces. Task 53 adds the internal Markdown Documentation Portal; Task 54 adds the protected, read-only Updates / Changelog page.

Provider & Model Management — Task 49

The page at /ui/providers lists/views and creates/removes Providers through GET /api/providers, GET /api/providers/{provider_id}, POST /api/providers, and DELETE /api/providers/{provider_id}. Provider reads require provider:read; creation and removal require provider:manage. Creation sends only the existing id and name fields; responses expose only id and configured type, not credentials or provider configuration. Provider removal requires confirmation.

Model assignments load through GET /api/models and GET /api/models/{agent_id} with model:read. Replacement uses PUT /api/models/{agent_id} with exactly provider_id and model_id and requires model:manage. Assignment data identifies the Agent by ID; Employee names are not part of the current Model API contract. The UI creates or modifies no Employees/Agents and accesses no Core internals. Browser sign-in/session integration is not configured; authenticated sessions with the relevant permissions remain required. Task 50 adds Task Management; Task 51 adds Project Management; Task 52 adds Activity / Logs; Task 53 adds the read-only Markdown Documentation Portal. The public Node.js documentation site remains separate from the Corporation UI.

Task Management — Task 50

The page at /ui/tasks lists Tasks and displays details through GET /api/tasks and GET /api/tasks/{task_id}, both requiring task:read. Creation uses POST /api/tasks with task:create; the supported fields are title, description, optional project ID, and at most one of Agent ID, role, or capability. Task IDs and status are generated by the API. Existing POST /api/tasks/{task_id}/dry-run uses task:read and previews routing without executing an Agent/Provider or mutating Task state. The API has no Task DELETE or lifecycle mutation endpoint, so the UI offers no delete/start/complete/cancel actions. A known persistence limitation means the optional project association is not reliably retained across TaskRegistry reloads. Authentication/session integration is not configured, so protected operations continue to require an authenticated session. No Core/registry/persistence access is added to browser code.

Project Management — Task 51

The page at /ui/projects lists and loads details with GET /api/projects and GET /api/projects/{project_id} using project:read. Project creation uses POST /api/projects and project:create, with only the supported name and optional description fields; the API generates Project ID and status. The API has no Project delete or lifecycle endpoint, so no such action is presented. The UI distinguishes empty results from failures, clears stale list/details after list refresh failures, and handles missing detail records. It uses same-origin requests and no Core/registry/persistence access. Browser authentication remains fail-closed and requires an authenticated session.

Activity / Logs UI — Task 52

The read-only page at /ui/activity uses only GET /api/activity, protected by activity:read. It uses the actual limit parameter (1–100, default 100) and optional task_id filter. The page shows only API fields: Activity ID, Task ID, event, and timestamp. Results are bounded API output and do not claim to represent the complete history. The endpoint has no detail route and intentionally omits message text. Manual refresh clears old records while loading and after errors; API failures are not shown as empty results. Same-origin authentication remains required and the browser UI adds no internal log access.

Conversation Foundation — Task 55

The Core now defines in-memory Conversation and Message records. Conversations accept ordered messages while open and can close only after pending messages reach a terminal state. Message lifecycle transitions are limited to pending → completed or failed. These records do not call providers, create Tasks, persist data, or provide a chat API/UI. Chat-to-Task workflows remain separate future work.

Documentation Portal — Task 53

The internal Corporation page at /ui/documentation lists and reads Markdown documents through GET /api/documentation and GET /api/documentation/{document_id}. Both protected routes require documentation:read and call a replaceable Documentation Application Service. The default source exposes only regular, top-level UTF-8 .md files from repository-root corporation_docs/; IDs are validated filename stems, titles use the first Markdown H1 or a filename fallback, and content is returned as Markdown text. Arbitrary paths and escaping symlinks are not exposed. The UI uses same-origin requests, renders content as text, clears stale content on failures, and distinguishes loading, empty, authentication, forbidden, missing-document, and general errors. It is a curated file-backed portal, not an AI-managed Knowledge System, and has no editing or publishing actions. It is separate from this public Node.js documentation website.

Updates / Changelog — Task 54

The internal page at /ui/updates lists curated records through protected GET /api/updates, requiring updates:read. Records come from the manually maintained repository-root corporation_updates.json manifest and include only an explicit date, development/release type, title, and summary. Maintainers add entries for verified changes; dates and versions are never inferred from Git history. This internal Corporation feature is separate from this public documentation site's milestone summary at updates.html.

Implementation caveats

  • Employee, Agent, Provider, Corporation, and Node registries are in-memory; broad administrative persistence is not implemented.
  • Tool and approval foundations are not wired into task execution as enforcement gates.
  • TaskRegistry does not currently persist or reload project_id.
  • Integration proposals, analysis, evaluation, sandbox records, and preparation records are in-memory foundations.
  • The public documentation site is a separate Node.js presentation app and does not connect to the Corporation runtime.

Individual Employee Chat — Task 56

The in-memory Core EmployeeChatService accepts exactly one explicit Employee or Agent selection. An Employee must have an assigned, registered Agent. Conversation targets capture fixed Employee/Agent IDs and employee or agent scope; later Employee reassignment does not retarget existing conversations. Callers explicitly record ordered messages and pending → completed or failed outcomes, using Task 55 lifecycle rules. Immutable snapshots prevent callers from modifying the service-owned records. There is no automatic response generation, provider interaction, context retrieval, persistence, Conversation API/UI, Orchestrator coordination, or Task creation/execution.

Chat Context — Task 57

Added caller-supplied context bounded to 8192 UTF-8 bytes per conversation, with atomic replacement, isolation, and clearing on successful closure; no retrieval, persistence, provider calls, or chat API/UI. Trusted Core callers enforce authorization and relevance before supplying text; caller-held copies cannot be revoked. The Documentation Portal remains file-based and read-only.

Corporation Chat — Task 58

Added local Corporation Chat CLI commands with explicit coordinator Agent identity, Orchestrator-mediated replies, bounded prompts, isolated conversation history, and recorded response failures; no automatic Task creation or Web/API chat. Local chat is trusted and in-memory; explicit sends may call the configured provider, while tests use fakes. The file-based Documentation Portal is unchanged.

Corporation Task Creation via Chat — Task 59

Added immutable chat-to-Task reviews of completed user messages with explicit project and Agent routing; human CONFIRM creates a pending persisted Task without execution, and consumed reviews cannot be replayed. Reviews and local human confirmation are separate from sending chat messages. Review state is in-memory; uncertain creation failures require human inspection.

AI Activity Visualization — Task 60

Added permission-aware Task lifecycle progress to the Activity page using protected Task detail reads, with explicit pending/running/completed/failed states, separate access errors, stale-response rejection, and no fabricated provider telemetry. Select a Task ID and refresh for a current lifecycle snapshot. task:read is checked independently of activity:read. Local chat has no browser telemetry.

Memory Architecture — Task 61

Defined immutable scoped memory records with explicit owners, note/summary types, required provenance and expiry, retention opt-in, and exact owner/scope retrieval checks without automatic sharing or storage. Trusted callers bind owner identity and validate sources. Existing legacy key-value stores remain separate. Persistent conversation notes are explicitly supported by Task 62; no automatic transcript archive is added.

Persistent Conversation Memory — Task 62

Added explicitly opted-in SQLite conversation memory with immutable bounded records, owner/conversation-scoped retrieval, expiry enforcement, explicit deletion and scoped cleanup, and corrupt-data rejection; chat messages are never saved automatically. Retained notes survive chat closure until expiry/deletion. Cleanup is explicit; SQLite is plaintext. No memory HTTP/UI interface or automatic transcript archive is added.
