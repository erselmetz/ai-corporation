Documentation

A guide to the Corporation's implemented foundations and documented direction.

Current implementation

The application includes a local Python command-line system and a FastAPI interface. It models Corporation and Node identity, Employees and technical Agents, a Provider/Model boundary, persisted Tasks and Projects, deterministic task routing, lifecycle logging, and dry-run inspection. The current runtime uses Ollama for provider execution; the dashboard does not invoke it.

Tasks 1–49 are documented as completed foundations, including the authorized APIs, read-only Activity support, the FastAPI Web UI foundation, the Corporation dashboard, Employee Management, and Provider & Model Management. “Completed” describes the implemented milestone scope; it does not imply production completeness. Tasks 50–54 remain planned. The task roadmap separates completed work from planned items.

FastAPI resources

API resource routes use an injectable authentication backend and permission checks, then call CorporationApplicationService. The default backend rejects every request until an application supplies authentication. This foundation does not configure a production identity provider or token system. The public / and /health endpoints remain separate from protected Corporation resources.

Task API — Task 43

  • GET /api/tasks and GET /api/tasks/{task_id} require task:read.
  • POST /api/tasks requires task:create.
  • POST /api/tasks/{task_id}/dry-run requires task:read.

Creation accepts title, description, optional project ID, and at most one existing routing selector: Agent ID, role, or capability. The Core/Application Service generates the ID. Responses use explicit schemas with task and routing fields; internal result/error fields are omitted. Project and routing relationships are carried by identifiers/requirements; the existing TaskRegistry does not persist or reload the project ID.

Missing Tasks or referenced Projects return 404. Invalid routing/domain conditions return 400; invalid request data is rejected by FastAPI/Pydantic with 422. Dry-run previews routing without executing Agents/Providers or mutating Task state. No HTTP task execution or lifecycle-mutation endpoint is exposed.

Project API — Task 44

  • GET /api/projects and GET /api/projects/{project_id} require project:read.
  • POST /api/projects requires project:create.

Project responses expose only ID, name, description, and existing status. Creation accepts a name and optional description; the Application Service generates the ID and uses the existing ProjectRegistry persistence. Missing Projects return 404, duplicate ID conflicts return 409, and invalid request bodies return 422. No Project lifecycle mutation or task-list endpoint is exposed.

Other implemented resources are Corporation status at GET /api/status; Employee list/detail/create/delete; Agent list/detail; Provider list/detail/create/delete; and Model assignment list/detail/replacement. These use explicit API schemas and permissions. The API does not expose raw registries.

Activity API — Task 45

GET /api/activity requires activity:read and returns the newest 100 activity entries by default. The optional task_id filter uses the existing task-specific log association, and limit can be set from 1 through 100. Responses expose only the stored log ID, Task ID, event name, and timestamp; message text is intentionally omitted because it can contain internal error details. No individual-log or write endpoint is exposed.

Web UI and dashboard — Tasks 46–47

The Corporation Web UI is served by FastAPI at /ui, with application-owned CSS and browser-native JavaScript under /ui/static/. Task 47 provides a read-only dashboard using the existing protected status, Employee, Agent, Provider, Model, Task, Project, and Activity APIs. The browser sends same-origin credentials; it adds no API credentials and no unauthenticated data aggregation route. No browser sign-in/session integration is configured, and the default API authentication backend rejects requests. Accordingly, the dashboard shows distinct sign-in-required, forbidden, and general failure states with retry rather than treating failed requests as empty results. Provider/model identifiers do not establish availability or health; Task responses do not contain timestamps, so the dashboard does not claim recent Tasks. Activity shown is bounded to eight newest-first records. It performs no Core/registry/SQLite access, provider calls, or task/agent execution.

The standalone public Node.js documentation website in docs/ remains a separate application and is not connected to this Corporation Web UI.

Employee Management — Task 48

The Employee Management page is served at /ui/employees, links back to the dashboard, and uses the existing /api/employees endpoints only. Listing and detail reads (GET /api/employees and GET /api/employees/{employee_id}) require employee:read. Creation (POST /api/employees) and removal (DELETE /api/employees/{employee_id}) require employee:manage. The create request accepts exactly the existing supported fields: caller-provided id, name, role, and optional responsibilities; Agent association is not accepted or modified. Removal requires explicit confirmation. The page presents authentication-required, forbidden, conflict, validation, missing-record, and general failure states. Browser sign-in/session authentication remains unconfigured, so protected data and actions require an authenticated session. The API itself calls CorporationApplicationService; the UI does not access registries or persistence directly.

Tasks 49–54 remain planned: Provider/Model, Task, Project, and Activity interfaces, followed by the Corporation documentation portal and updates page.

Provider & Model Management — Task 49

The page at /ui/providers lists/views and creates/removes Providers through GET /api/providers, GET /api/providers/{provider_id}, POST /api/providers, and DELETE /api/providers/{provider_id}. Provider reads require provider:read; creation and removal require provider:manage. Creation sends only the existing id and name fields; responses expose only id and configured type, not credentials or provider configuration. Provider removal requires confirmation.

Model assignments load through GET /api/models and GET /api/models/{agent_id} with model:read. Replacement uses PUT /api/models/{agent_id} with exactly provider_id and model_id and requires model:manage. Assignment data identifies the Agent by ID; Employee names are not part of the current Model API contract. The UI creates or modifies no Employees/Agents and accesses no Core internals. Browser sign-in/session integration is not configured; authenticated sessions with the relevant permissions remain required. Tasks 50–54 remain planned: Task, Project, and Activity UIs, then the Corporation-integrated documentation portal and updates page. The public Node.js documentation site remains separate from the Corporation UI.

Implementation caveats

  • Employee, Agent, Provider, Corporation, and Node registries are in-memory; broad administrative persistence is not implemented.
  • Tool and approval foundations are not wired into task execution as enforcement gates.
  • TaskRegistry does not currently persist or reload project_id.
  • Integration proposals, analysis, evaluation, sandbox records, and preparation records are in-memory foundations.
  • The public documentation site is a separate Node.js presentation app and does not connect to the Corporation runtime.
