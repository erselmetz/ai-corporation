ERSELMETZ AI CORPORATION

ERSELMETZ AI CORPORATION is an actual software system implementing a virtual/simulated AI organization. The organization is the domain model; the software implements its current capabilities.

This page summarizes the implemented local Python command-line system. Planned capabilities are marked as future work.

Implemented architecture

Corporation identity
└── Node / installation
    └── Runtime Context (validated Corporation + Node IDs)

Command interface
└── Orchestrator
    ├── Task lifecycle, SQLite persistence, and logs
    └── Deterministic Task Router
        ├── Explicit Agent assignment
        ├── Required Employee role
        └── Required Agent capability
            └── Agent → Provider (currently Ollama) → Model

Standalone foundations: Client/Business adapter, Tool registry,
in-memory Human Approval registry

Employee != Agent != Provider != Model. An Employee is an organizational identity and may be associated with a technical Agent. The Agent carries capabilities and Provider/Model identifiers.

Task routing and persistence

Role and capability routing intent is stored on the Task and in SQLite; it is not eagerly converted to assigned_agent.

PriorityRoute
1Explicit assigned_agent
2required_role → registered Employee → associated Agent
3required_capability → matching Agent
4Routing failure if no suitable Agent is found

Routing is deterministic. There is no AI/LLM-based selection and no automatic fallback Agent. Dry-run reports the route without calling the Provider or changing Task state. CLI routing overrides are temporary.

Implemented scope and limits

  • Task lifecycle, orchestration, task logs, SQLite tasks/projects, and memory stores.
  • Agent/Employee registries and management; Provider/Model commands; Ollama is the only implemented Provider.
  • Corporation/Node identity models and runtime relationship validation; local IDs are configured in startup code.
  • ClientRequest validation and a BusinessLayer-to-Task adapter, not an HTTP intake service.
  • Tool abstraction/registry is not wired to Agent execution; no concrete built-in tools or enforced permissions.
  • Approval request state is in-memory and not an execution gate.
  • Known limitation: TaskRegistry does not persist or reload project_id.
  • Tasks 26–30 add the in-memory proposal foundation, GitHub discovery, bounded analysis/learning, evidence-backed evaluation, and proposal generation; Tasks 31–33 add the sandbox foundation, execution boundary, and optional Docker backend; Task 34 adds controlled source staging.

Integration Proposal foundation

An IntegrationSource describes an external source independently from internal Employees, Agents, Providers, and Models. An IntegrationProposal captures the requested purpose, source, evaluation/approach/risk notes, timestamps, lifecycle, and approval request.

The proposal lifecycle is Discovered → Analyzing → Evaluating → Proposed → Sandboxed → Tested → Review Required → Approved → Integrated, with Rejected and Failed outcomes. Sandbox records are separate: creating one does not transition the proposal. Approval and integration are separate states. An IntegrationExecutionRecord is a distinct audit/state record, can only be created for an approved proposal, and performs no execution or project modification.

Proposals and execution records are currently in-memory only. The execution record does not perform integration work. Capability names in the model are requested-scope vocabulary, not grants or enforcement.

Public GitHub source discovery (Task 27)

SourceDiscovery is a source-adapter boundary; GitHubRepositoryDiscovery accepts validated HTTPS public GitHub repository sources and calls only fixed GitHub REST API endpoints. It returns typed repository metadata, latest release details when available, and README availability/size plus a bounded plain-text excerpt where safe. Expected API, rate-limit, network, not-found, invalid-source, and malformed-response cases are explicit errors.

Discovery collects metadata only. Repository content is untrusted data, not instructions; discovery does not clone, install, execute, evaluate, sandbox, modify ERSELMETZ, approve, or integrate anything. A future proposal can reference a discovery result by ID.

Bounded source analysis / learning (Task 28)

SourceAnalyzer accepts a Task 27 SourceDiscoveryResult; GitHubRepositoryAnalyzer inventories the repository tree and reads selected documentation and dependency manifests from fixed GitHub API endpoints. Typed results keep direct file/structure facts separate from evidence-linked observations about purpose, frameworks, and potential capabilities. Those observations are not verification or integration recommendations.

Analysis is bounded to 50 relevant files, depth 8, four documentation files, 48 KiB per file, 256 KiB of decoded content, and a 2 MiB tree response. Truncated or limited results are marked incomplete. All content remains untrusted text: no code execution, shell commands, installation, local writes, evaluation scores, approval, or integration occur. Results are in-memory only; there is no analyze CLI because discovery results are not persisted.

External source evaluation (Task 29)

GitHubRepositoryEvaluator consumes only existing discovery and analysis results and produces typed, evidence-linked findings about capability fit, architecture, dependencies, license metadata, bounded security observations, maintenance signals, and integration complexity. The result summarizes strengths, concerns, unknowns, and requirements; unknown evidence remains unknown, and no score or ranking is produced.

Evaluation is decision support only. It does not approve integration, create or transition proposals, execute external code, install dependencies, modify ERSELMETZ, or commit/push. A later proposal, review, and human approval remain separate controlled stages. Results are in-memory only.

External integration proposal generation (Task 30)

GitHubIntegrationProposalGenerator consumes already-produced discovery, analysis, and evaluation results to create a structured IntegrationProposal. It preserves source/evaluation traceability and evidence-backed strengths, concerns, unknowns, dependency/license/security observations, and requirements. Missing evidence remains explicitly unknown; no score or ranking is created.

The generated proposal describes a possible integration and stops at PROPOSED. It does not imply approval, automatically register itself, execute external code, install dependencies, clone repositories, or modify ERSELMETZ or Git state. The existing registry can store it when a caller explicitly registers it. Controlled review and human approval are required before integration.

Integration sandbox foundation (Task 31)

IntegrationSandbox has an explicit identity linked to a PROPOSED proposal and its discovery result. The separate in-memory IntegrationSandboxRegistry supports create, get, list, explicit lifecycle transitions, and destroy without changing proposal state. Lifecycle states include Configured, Ready, Running, Completed, Failed, and Destroyed; Task 32 still blocks entering Running because there is no actual isolated backend.

SandboxIsolationPolicy defines restrictive filesystem, network, process, environment, credential, and resource-limit defaults. These settings are policy metadata only, not enforcement. Task 31 does not execute code, install dependencies, create containers or VMs, enforce network/filesystem isolation or resource limits, modify the host or ERSELMETZ, or add CLI/persistence. Actual isolation requires a future isolated backend.

The implemented external-source pipeline is Discovery → Analysis/Learning → Evaluation → Proposal → Sandbox Foundation. Testing, review, human approval, and integration remain separate stages.

Sandbox execution boundary (Task 32)

SandboxExecutionRequest and SandboxExecutionResult define typed execution inputs and outcomes. SandboxExecutor defines the boundary, and SandboxBackend describes future prepare, execute, collect-result, and cleanup operations. The default UnavailableSandboxBackend reports backend none and no isolation enforcement.

A valid request without an implemented isolated backend returns BLOCKED, with no exit code or execution measurements; the sandbox remains READY. Task 32 validates relative entrypoints, sandbox/proposal linkage, timeout, environment mode, and requested resource bounds. Requests do not carry host environment variables or credentials.

The executor abstraction is not actual isolation enforcement. Task 32 does not execute external code or host processes, invoke shell/subprocess, run Docker/Podman/VMs, install dependencies, clone repositories, grant network access, enforce filesystem/resource limits, or inject credentials. The implemented architecture is Integration Sandbox → Sandbox Executor → Sandbox Backend → Actual Isolated Runtime (future).

Docker sandbox backend (Task 33)

DockerSandboxBackend implements the backend contract through the optional official Docker Python SDK; DockerSandboxExecutor coordinates the registered sandbox lifecycle and cleanup. The SDK is not a base dependency and is never installed automatically. Without the SDK, a Linux Docker daemon, an explicitly configured digest-pinned image allowlist, and the approved image already present locally, the request is blocked. Images are never pulled automatically.

Containers request network disabled, no host mounts or Docker socket, no credentials or host environment, non-privileged mode, non-root numeric user, all capabilities dropped, no-new-privileges, read-only root filesystem, memory/CPU/PID/disk limits, bounded timeout, output collection, and forced cleanup after completion/failure/timeout. Arguments are passed structurally to a container entrypoint. If Docker cannot apply requested controls, execution fails closed; no host subprocess fallback exists.

Docker container isolation is the current execution mechanism for the sandbox backend when configured, but sandbox execution is still an experimentation layer and does not imply approval or integration. The executor/backend abstraction is distinct from enforcement: Docker performs the isolation only for an actually created container. No repository clone, source staging, dependency installation, approval, or integration is performed.

Architecture: Integration Sandbox → SandboxExecutor → SandboxBackend → DockerSandboxBackend → Disposable Docker container.

Controlled source staging (Task 34)

SourceStager defines an inert preparation boundary; GitHubSourceStager accepts only a validated public GitHub SourceDiscoveryResult. It uses HTTPS to a fixed GitHub API archive endpoint and validates redirects to the corresponding codeload repository only. It does not use Git/host credentials or environment proxy settings, and never invokes shell, subprocess, Docker, or staged instructions.

Compressed archive size, archive member count, file count, total expanded bytes, individual file size, and path depth are bounded. Members are validated before any extraction; absolute/traversal paths, conflicting paths, links, and special files are rejected. Source is written into a dedicated temporary workspace outside the project repository. Failed attempts clean up partial workspaces; successful results include discovery linkage, counts, status, timestamps, and SHA-256 identity metadata. Hashes do not establish trust or approval.

Staging does not execute source, install dependencies, change proposal lifecycle, modify the project or Git state, or integrate code. The pipeline is GitHub Source → Discovery → Analysis/Learning → Evaluation → Proposal → Sandbox → Controlled Source Staging → Sandbox Source Binding → Sandbox Executor → Docker Backend → Isolated Container. Staging prepares data only; Docker execution remains experimentation and does not imply proposal approval or integration.

Sandbox/source binding (Task 35)

SandboxSourceBindingRegistry associates a completed staging result with its registered sandbox and proposal after checking proposal/sandbox/discovery/staging linkage. It requires the real workspace to be a direct child of the explicitly configured staging root, match the staging-ID-derived name, remain outside the project, and contain no symlink or non-regular file. It recomputes the Task 34 content hash, file count, and total size; mismatch or unsafe paths fail closed.

The resulting in-memory binding preserves source/archive SHA-256 metadata but is not a trust or approval signal. Binding does not transition proposal, sandbox, or task state; it does not call the executor or Docker, execute files, install dependencies, or expose host paths.

Sandbox execution preparation (Task 36)

ExecutionPreparationRegistry resolves the existing proposal, sandbox, completed staging result, and registered source binding. It rechecks their ID relationships, the staging-controlled workspace boundary, the sandbox’s restrictive policy metadata, and the current content hash/file count/byte size. It creates an immutable, in-memory readiness record with source identity, policy snapshot, timestamp, validation notes, and limitations. A future execution layer can revalidate the recorded workspace with verify_workspace immediately before use.

The preparation request accepts no command/entrypoint, host environment, or credential references. Preparation is validation only: no source execution, subprocess, shell, Docker, package installation, network download, lifecycle transition, approval, or integration occurs. Matching SHA-256 is identity metadata, not proof of safety or trust. Pipeline: Source Staging prepares controlled source → Sandbox Source Binding associates it → Execution Preparation validates readiness → Sandbox Executor remains the execution boundary → Docker Backend provides isolation only for a separately enabled future execution.

Future roadmap

Dependency installation → Testing → Review → Human Approval → Integration → Monitoring; richer orchestration and multi-Agent collaboration; AI-based routing and advanced Provider/Model selection; Agent-to-Agent communication; networking and Node Discovery; Authentication, Authorization, Encryption, Offline Mode, Synchronization, and Conflict Resolution; QA guardian; richer Tools/MCP; open-source coding, repository, terminal, browser/computer, voice, and Git/GitHub integrations; controlled self-improvement.

The Corporation is intended to provide governance, organization, orchestration, identity, task management, routing, approval, and coordination—not to unnecessarily reinvent mature open-source coding and agent infrastructure. Listed integration areas are plans, not current integrations.

Controlled improvement: Discover → Analyze/Learn → Evaluate → Proposal → Sandbox Foundation → Controlled Source Staging → Sandbox Source Binding → Sandbox Executor → Docker Sandbox Backend → Disposable Container → Test → Review → Approve → Integrate → Monitor. Unrestricted autonomous self-modification is not the current design.
