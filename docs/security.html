Boundaries and limitations

Security

This page documents controls present in the current implementation and distinguishes them from policy metadata or future plans. It is not a security certification.

Documentation-site isolation

The Node.js website inside docs/ is a presentation-only site. It reads and serves an explicit allowlist of documentation files. It does not import Python application code, connect to FastAPI, databases, Ollama, internal APIs, registries, or runtime state, execute Corporation tasks, control Agents, or modify the Corporation. It works independently when the Corporation is offline.

The Node server uses only built-in modules, supports GET/HEAD, serves an explicit file allowlist, and sends basic content-type, referrer, and content-security headers. It has no API or dynamic Corporation data endpoints.

External source and sandbox boundaries

  • GitHub discovery uses fixed public HTTPS API endpoints; source content remains untrusted data.
  • Web research fetches only explicitly supplied HTTPS URLs on exact allowlisted hosts, follows no redirects, disables environment proxies, and labels retrieved text as untrusted evidence; it does not execute or forward retrieved content to Agents or Providers.
  • Task 90 browser inspection reuses the exact-host HTTPS policy, strips scripts, styles, resource URLs, and event attributes before rendering, blocks browser requests, and uses an ephemeral context with JavaScript, downloads, interaction, and local-file access disabled. It is static read-only inspection, not general computer control; page content remains untrusted evidence.
  • MCP coding-tool proposals receive only explicitly selected file contents and return bounded diffs restricted to selected paths. The adapter applies and executes no code; MCP servers remain trusted host processes and are not OS-sandboxed.
  • Analysis is bounded and observational. It does not execute code or install dependencies.
  • Staging validates archive paths, types, counts, sizes, and depth before writing into a controlled temporary workspace outside the project.
  • Binding and preparation recheck paths, linkage, and content hashes. A hash identifies bytes; it does not establish that they are safe or trustworthy.
  • The optional Docker backend requests restrictive isolation settings and fails closed when required controls are unavailable. There is no host-process fallback.
  • Preparation is metadata only: it does not execute staged source or transition proposals to approval/integration.

Gemini model-catalog boundary — Task 91

The on-demand adapter targets one fixed HTTPS endpoint, accepts the API key only through explicit trusted backend configuration, and transmits it only in the x-goog-api-key header. It never returns, logs, or places the key in a URL; request errors and audit records omit credentials and raw response bodies. Responses are capped at 512 KiB per page and pagination is limited to five pages. Audit events contain operation, time, outcome, page/model counts, completeness, and a safe failure code; they are returned to the caller but not persisted automatically. This listing-only capability has no key-entry UI, general credential store, model execution, Task/Agent assignment, or background calls.

Capability inventory boundary — Task 92

The capability registry is a read-only aggregation of Agent declarations, Tool registrations, integration request-scope metadata, and only caller-supplied Gemini catalog snapshots. It distinguishes source evidence and preserves source timestamps; it does not contact services, authorize callers, grant capabilities, verify Agent expertise, execute Tools, or change assignments. The returned records are bounded and immutable; reads across independent registries are sequential rather than atomic.

API authentication boundary

FastAPI routes have injectable authentication and permission-checking dependencies. The default backend rejects all requests; a production identity provider, credential/token validation, and deployment-specific authorization policy are not configured. Permission names document route requirements, not a user-management or role-administration system. Do not deploy protected API operations as though production authentication were configured.

Position management boundary — Task 107

Position routes require distinct position:read or position:manage permissions and are available only in explicit local-owner mode; these permissions do not change the default fail-closed API. Position titles grant no authority. Records are bounded and process-local, with no durable storage or Task/workflow linkage. Reporting cycles, stale updates and deletion while referenced or history-bearing are rejected. Employee IDs are references only; position operations do not alter Employee roles or Agent/model assignments. If a principal has position read but not Employee read, the UI withholds Employee choices and preserves an existing Employee reference.

Manual assignment and individual Employee chat boundary — Task 108

Local model and Gemini assignment requires a browser preview of the selected Agent identity, old/new model, privacy handling, assigned Tasks, and the current principal's coordinator and Employee conversations; failed or incomplete impact reads abort the mutation. The server checks the expected Agent assignment to reject stale previews. Supported in-process assignment paths reject active Agent execution, and task dispatch verifies the selected provider/model before generation so a concurrent reassignment fails rather than silently changing the job. Existing Task Agent IDs and conversation snapshots are not rewritten. Individual Employee chat routes require separate employee-chat:read, employee-chat:start, employee-chat:send, or employee-chat:close permissions, granted only by explicit local-owner mode; the default API remains fail-closed. Each conversation belongs to one authenticated principal and snapshots its registered Employee, Agent, provider, model and provider instance. Only the current request and bounded recent conversation history are sent; Employee profiles and Task content are not attached automatically. Gemini turns require separate per-turn consent, and recognized API-key pastes are rejected before storage/provider calls. Chats are bounded and process-local, with no automatic retry. The existing one-Gemini-Agent limit remains; switching requires disconnect/reconnect. Assignment synchronization does not cover direct registry mutation, external processes, or multiple application instances.

Capability assignment policy boundary — Task 109

The local-owner assignment policy is disabled by default and protected by separate assignment-policy:read and assignment-policy:manage permissions; default API access remains fail-closed. It stores bounded policy data only in process memory. Recommendations are read-only: they do not change Agent assignments, reserve capacity, call providers, connect online models, send data, or imply Gemini consent. Eligibility requires a registered and owner-allowed provider, a fresh owner-recorded inventory reference, configured Task 71 admission capacity, an explicit owner-unit budget, and fresh positive tested evidence for all Agent-declared capabilities. Declarations, absent/stale evidence, unavailable access/capacity, and unknown costs are surfaced rather than treated as proof. Candidate inventories, evidence outcomes/references, and cost estimates are caller-supplied and not independently verified. Provider health, compatibility, hardware feasibility and execution readiness remain unknown. Online suggestions require a separate policy opt-in. Existing manual assignment remains authoritative, and the Task 108 preview/confirmation path is the only override. Disabling the policy fully undoes policy state because it never applies an assignment; any confirmed manual assignment must be reversed through the existing setup flow. Policy data is lost on restart.

Coordinator proposal review boundary — Task 110

Coordinator text never creates a Task by itself. The explicit local-owner proposal API requires the separate chat-task:create permission and same-origin CSRF protection; it does not grant general task:create. A proposal is scoped to its authenticated principal and completed assistant message, expires after 15 minutes, and must be confirmed using the exact server-generated digest. Confirmation rechecks conversation ownership/status, source content, coordinator, responsible Agent, Project and selected owner-authorized memory context. Proposal state and duplicate-fingerprint protection are in process memory only; multiple app instances and direct database/registry changes are outside the guarantee. Confirmation consumes the proposal before existing persistence to prevent an uncertain creation from being retried. It creates only a pending Task and never executes a Task or Tool. The durable Task stores source/context references and reviewed expected outcome/evidence, but no copied memory text or durable confirmer field.

Controlled worker dispatch boundary — Task 111

Dispatch requires the distinct task:dispatch permission and an explicit owner confirmation; local-owner writes also require same-origin CSRF verification. The service admits one pending Task only after validating its Project/context, current Agent route and existing Task 68 global/provider/model slots. Provider calls are limited to configured loopback Ollama. Cloud Providers and Tools are not invoked, and no automatic retry or replay occurs. Claims persist across restart for inspection only; uncertain work requires explicit human resolution and never implies verified outcomes. The standard local launcher does not configure capacity, so the feature fails closed until an embedding host configures budgets. Cross-process coordination and exactly-once execution are not guaranteed.

Local Gemini credential and consent boundary — Tasks 105–106

Gemini onboarding and generation routes are mounted only by the explicit loopback local-owner app. Only the standard Google AIza API-key shape is accepted by online setup; unsupported formats are rejected before catalog/network calls. A restricted API key is sent to the fixed Google API endpoint, kept in process memory for at most one hour, and removed on disconnect, staged-key erasure, expiry or restart. The registered adapter holds only a key digest; credentials are not persisted or put in chat transcripts. Coordinator chat rejects the supported Gemini key shape and GEMINI_API_KEY/GOOGLE_API_KEY assignments before storing a turn or calling a provider, and guides the owner to the separate setup form. This detection is best-effort, not a general secret scanner; unsupported/novel formats must not be entered in chat. Each online chat turn requires explicit consent for the message, recent history and configured context. Generation is bounded and has no retries or fallback. A connected key must be explicitly disconnected/erased before entering a replacement. No app-level dollar cap is enforced, and external use of the API key is not counted. The default API continues to reject unauthenticated access.

Known gaps

Encryption, networked Nodes, durable approval records, and an apply/checkpoint consumer for maintenance approvals are not implemented. Task 83 provides an in-memory approval workflow for exact maintenance patch/source hashes; its API requires maintenance:approve, but the configured backend must grant that permission only to human reviewers. The workflow is not yet consumed by a change-application path. Tool permissions are not enforced by a tool-execution policy. Do not infer production readiness from foundation milestones or security-related design metadata.

Multiple provider connection boundary — Task 112

Connection management APIs are mounted only in explicit local-owner mode and require separate provider-connection read/manage permissions plus same-origin CSRF for writes; the default API does not mount them. Only loopback HTTP Ollama and Gemini connections are supported. Gemini keys are connection-scoped, accepted through a bounded request body, held in process memory and omitted from status/API responses; removal refuses assigned providers and active use. Ollama URLs reject non-loopback hosts and credentials, and requests disable redirects and environment proxies. Owner-confirmed Agent assignments use fresh supported catalogs and compare the previous assignment; existing chats fail closed on stale routes instead of silently switching connections. Software request-slot limits enforce admission but do not prove hardware feasibility. The inherited Gemini call/output bounds do not enforce a dollar spend ceiling; billing remains external. Process-local locks do not coordinate direct registry changes or multiple application instances.
